# 迷わないおでかけ紙

高齢の家族が持つA4両面の「今すること」案内を、家族がPCで作成するためのVite + React + TypeScriptアプリです。SSR/SEOは対象外です。

## ローカル実行

```bash
npm install
npm run dev
```

ブラウザの検索結果では、固定PoCの列車・到着駅構内を表、駅外徒歩を裏としてA4両面でプレビュー・印刷します。

安全ゲートのユニットテストは次で実行します。

```bash
npm test
```

## 現時点でできること

- 大門 → 赤羽橋 → 2番ホーム → 赤羽橋口 → 東京タワーの固定往路をA4両面でプレビュー・印刷
- 表は出発駅の発車時刻・行先・乗車ホーム、到着ホームから出口までの大きな構内案内。出発駅の構内経路は作らない
- 裏は出口から東京タワーまでの徒歩順序図と徒歩案内。公開元が地図形状を提供しないため、方位・縮尺を示さない順序図として表示
- 出発駅・目的駅・出発日時は入力可能。ただし検索対応範囲は平日の大門→赤羽橋直通のみ

## データ設計と流れ

`Trip`（移動と列車の脚） + `StationGuide`（人が根拠を確認した構内動線） + `WalkingRoute`（駅出口から目的地） + 連絡先を `PrintableGuide` に集約し、表示層へ渡します。

```
実データ / fixture → GuideRepository → PrintableGuide → A4表・A4裏
```

`src/domain/types.ts` は提供元に依存しないモデルです。`StationGuide` は公式根拠URL、信頼度、人による確認情報（あれば）、代替の安全案内を扱います。公式GTFS-Pathwaysから事実として導ける部分は人手レビューなしでも出力できますが、由来・取得日・人手レビュー有無を区別します。LLMによる駅構内動線の推測・生成はしません。

## fixture である箇所

`src/data/fixtures/yamato-to-kozashibuya.ts` の列車時刻、徒歩距離・所要時間・概略地図・徒歩手順はfixtureです。列車到着ホームも「要 実データ照合」としています。高座渋谷駅の「ホーム中央の上り階段・エスカレーター→西口改札→西口」の文言は依頼内容を初期値にしていますが、`confidence: needs-review` であり、公開・実運用前に公式構内図と現地/事業者確認で更新が必要です。

`confidence: verified` でない駅構内または徒歩経路を含む紙には、赤い「検証用の案内です」警告を印刷する。この警告がある紙を持ち歩き用の完成案内として使わない。

地図は外部タイルや公開ルーティングAPIに依存しない概略SVGです。実用化時に、利用許諾を確認した地図・経路供給元または人が確認した経路形状へ置換します。

## 駅構内ルーティング PoC（大江戸線12駅へ展開する共通基盤）

`src/data/fixtures/oedo2026-*-gtfs-pathways.json` には、東京都交通局の2026-09-17 GTFS-Pathwaysフィードから公開対象12駅の `stops.txt` / `pathways.txt` 相当を同一スクリプトで抽出して格納しています。すべて共通の `extractGtfsPathwaysStation` を通すため、駅ごとの変換処理・案内文・経路を持ちません。出典は東京都交通局 鉄道関連情報（GTFS-Pathways）、ライセンスは CC BY 4.0 です。

`src/domain/indoorRouting.ts` は、このデータを有向グラフに正規化し、Dijkstraで探索します。エッジ種別はGTFSの `pathway_mode` に従い、通路・階段・動く歩道・エスカレーター・エレベーター・改札・退出改札を区別します。`shortest` / `avoid-stairs` / `elevator-priority` の重み付け拡張点を持ちます。

`wheelchair-accessible` も将来の選好として型に持つが、現在のGTFS-Pathwaysだけからは判定しない。幅員・段差・勾配・エレベーターの稼働状況などの確認済みデータがないため、この選好では探索結果を返さず、未対応理由を返す。

12駅へ展開するため、`src/data/adapters/gtfsPathwaysAdapter.ts` はGTFSの `stops.txt` / `levels.txt` / `pathways.txt` 相当の行を駅単位の共通形式へ抽出する。駅所属の判定は `parent_station` の親子関係だけで行い、駅名の部分一致や座標近接では推測しない。ZIP取得・認証・ブラウザ通信はこのアダプターの外に置く。

`src/data/catalogs/oedo2026IndoorStations.ts` には、2026-09-17に公開告知された12駅名と、20260917版GTFS-Pathwaysの `location_type=1` から確認したstation IDを収録する。`src/data/catalogs/oedo2026IndoorDatasets.ts` は12駅の抽出JSONを登録する共通レジストリで、画面・グラフ・レビュー・`StationGuide`生成はすべて同じ形を受け取る。駅固有の案内文や経路は登録していない。

`validateIndoorDatasets` は全駅について共通の `buildIndoorGraph` を実行し、各ホーム・出入口の組から `buildGtfsStationGuide` が事実として生成できる組を探索する。2026-09-20に取り込んだ同一ZIPでは **12/12駅の読込・グラフ生成成功、12/12駅の少なくとも1組のホーム→出口 `StationGuide`生成成功** だった。この数は「任意の到着列車から印刷可能な案内が確定した」ことを意味しない。列車方向からの到着ホーム、正確な降車位置、どの出口を採用するかは別の公式根拠が必要である。共通経路を生成できない駅が将来現れた場合は、失敗理由を診断へ記録し、経路を補完しない。

実データを追加する際は、[駅構内データ取り込み手順](docs/indoor-data-import-runbook.md) に従う。

20260917版GTFS-Pathwaysについては、12駅すべてをローカル抽出して件数を確認済みである。結果は [12駅GTFS-Pathways抽出監査](docs/oedo2026-gtfs-pathways-inventory.md) を参照。

開発用には、保存済みGTFS ZIPから一駅ぶんのJSONを再現可能に抽出するスクリプトを用意している。これはローカル作業用であり、ブラウザからデータ取得しない。

```bash
node scripts/extract-toei-gtfs-pathways.mjs \
  Toei-Train-GTFS-Pathway.zip 422 赤羽橋 \
  https://api-public.odpt.org/api/v4/files/Toei/data/Toei-Train-GTFS-Pathway.zip \
  'CC BY 4.0' 20260917 /tmp/akabanebashi.json
```

`auditIndoorGraph` は、ホームから正式な起点（配下のboarding areaを含む）を解決できるか、その各起点から出口まで実エッジ経路があるか、存在しないノードを参照する経路がないかを検証します。監査に通らないホーム起点は、どの経路選好でも利用者向け案内を生成してはいけません。

赤羽橋駅・国立競技場駅では、ホーム自体に `pathways.txt` の行がない場合でも、GTFS仕様どおりホームの子であるboarding area（`location_type=4`）へ経路を接続する。PoCは `parent_station` が示すこの正式な親子関係だけを用い、ホーム配下のboarding areaを候補起点として探索する。座標近接による仮想リンクは追加していない。

ホーム1番の11候補、ホーム2番の12候補は、いずれも赤羽橋口への実エッジ経路を持つことを確認した。ただしフィードには列車の実際の降車位置を一意に指定する情報がないため、候補のうち一つを紙用の案内として自動採用しない。利用者向けに一つの経路を出すには、乗車位置・到着列車・車両位置との対応、または人が確認した代表起点が必要である。

`VerifiedIndoorRouteAnchor` は、駅・ホーム・**正確なboarding area**・出口・確認者・確認日・公式根拠URLを一組にした追加レビュー情報である。実際の降車位置が分かる場合に、GTFSのみでは表せない起点からの経路を補足できる。これはGTFS由来の案内を出すための必須条件ではない。

レビュー記録は確認者、実在する `YYYY-MM-DD` の確認日、HTTPSの根拠URLが揃わなければ無効として拒否する。この検査は記録形式の最低条件であり、根拠内容の妥当性は別途人が確認する。

`buildGtfsStationGuide` は、同一ホーム配下の各boarding areaから出口へ至る候補を比較する。全候補で同一の末尾経路に加え、末尾より手前にある `pathway_mode=6`（fare gate）を**意味イベントとして保持**する。各イベントには「何個のboarding area候補で確認されたか」を provenance として保存するため、実際の降車位置を推測しないまま改札イベントを圧縮で失わない。改札名・案内板・右左・候補ごとに異なる未確定の通路は補完しない。`buildVerifiedStationGuide` は、これに正確な乗降位置等を補足する人手レビュー用の別経路である。

赤羽橋駅では、固定した平日の公式時刻表GTFSの `400613B0`（大門 `07:03` 発 → 赤羽橋 `07:05` 着、都営大江戸線・光が丘行）をPoC行程としている。`stop_times.txt` は駅到着時刻・順序・方向を持つ一方、番線を持たない。そのため `src/data/fixtures/akabanebashi-arrival-itinerary.ts` に、東京都交通局の公式資料で明示された「2番線（新宿・光が丘方面）ホーム」を別の根拠レコードとして登録し、両方が一致する時だけ `422P2` を `buildGtfsStationGuide` の起点に渡す。GTFSの方向や座標から番線を推測しない。

この接続により、A4表の列車欄は上記固定行程を、「降りたホーム」は公式資料由来の2番ホームを、「次にすること」はGTFS-Pathways由来の共通末尾と意味イベントを表示する。人手レビューは不要で、実際の降車位置・改札名・左右は表示しない。駅外徒歩は裏面に別情報源として表示する。公式の番線対応が欠ける駅／方向では、到着ホームも構内案内も自動表示しない。

番線根拠は [東京都交通局の公式設備点検資料](https://www.kotsu.metro.tokyo.jp/subway/kanren/inspection/pdf/inspection202509_04.pdf)、時刻表根拠は [東京都交通局の静的GTFS](https://api-public.odpt.org/api/v4/files/Toei/data/Toei-Train-GTFS.zip) である。いずれも取り込み日をfixtureに記録し、運行変更・番線変更の当日確定情報には使わない。高座渋谷駅の列車・徒歩fixtureとは混在させず、実際の降車位置と駅外徒歩が未接続であることを赤い警告で明記する。

## 赤羽橋駅 → 東京タワーの往路 PoC

固定往路の裏面は、`422N0012`（赤羽橋口）を**IDで明示的に**出発点とし、東京タワー（フットタウン）を目的地にする。座標近接で駅出口と徒歩経路を接続してはいない。`src/data/fixtures/akabanebashi-to-tokyo-tower.ts` は、[東京タワー公式の赤羽橋駅からの徒歩案内](https://en.tokyotower.co.jp/access/railroad/)を `WalkingRoute` に正規化したfixtureである。同サイトが公開する横断歩道・進行方向の手順と「徒歩5分」だけを収録する。

この徒歩経路はGTFS-Pathwaysではない。A4裏面に「目的地公式アクセス案内」として別出典・取得日・人手レビュー未実施を表示する。公式ページに距離、機械可読な地図形状、当日の通行可否がないため、それらは生成・表示しない。ゆっくり歩く目安は公式の5分を既存の倍率1.5で計算した約8分であり、実測値ではない。

## 入力による列車行程検索 PoC

`src/data/repositories/staticGtfsRailJourneyRepository.ts` は、ブラウザに置いたAPIキーや外部ルーティングAPIを使わず、公式の都営静的GTFSからローカル抽出した `trips.txt` / `stop_times.txt` 行を検索する。入力は出発駅、目的駅、出発日、出発時刻で、入力時刻以降で最初の直通便を返す。その `ScheduledRailLeg` を既存の `resolveArrivalPlatform` に渡すので、画面から入力しても到着ホームを固定値で渡さない。

現時点の対応範囲は、GTFS有効期間 `2026-03-14`〜`2026-12-31` の平日、登録済みの直通区間（大門→赤羽橋、大門→六本木、六本木→国立競技場）である。公式GTFSの `trips.txt` / `stop_times.txt` から機械抽出した `toeiOedoExtractedDirectLegs` を駅名の組み合わせで検索し、指定時刻以降で最初の便を返す。既定の `2026-09-21 07:00` では、東京タワーコースは `400613B0`（大門07:03発、赤羽橋07:05着）、国立新美術館コースは同じ `400613B0`（大門07:03発、六本木07:09着）、国立競技場コースは `400611B0`（六本木07:01発、国立競技場07:05着）が選ばれる。ホーム・出口・徒歩routeの公式対応がないコースは、列車結果だけを確認可能な未確定紙面として扱い、構内・徒歩案内を生成しない。

ODPTのライブAPI接続は未実装である。ODPTの認証情報とスキーマ、利用条件を確認した後は、同じ `RailJourneyRepository` をサーバー側の同期／検索実装に置き換える。ブラウザ側にトークンを埋め込む実装はしない。

`GuideStep.evidence` には、GTFS由来なら元エッジIDと起終点、レビュー文なら手確認の根拠URLを保持する。紙面には出さないが、管理画面・レビュー時に追跡できる。

PoC画面にはレビュー担当者用のローカル確認パネルがある。ここでは実データのホーム・boarding area・出口を選び、確認者・日付・根拠URL・紙面ラベルを追加して、GTFSの共通区間より精密な `StationGuide` を生成できる。生成された各ステップにはGTFSエッジIDまたは人手レビューの根拠を紐付ける。記録は同じブラウザの `localStorage` にだけ保存・再読込できる開発用機能であり、共有・正式承認は未実装である。編集後は保存済みと表示しない。

GTFSフィードにない経路時間、階段段数、案内板文言、右左、改札固有名、出口番号、車椅子適合性は自動生成しません。歩行空間ネットワークは経路探索の正本にせず、赤羽橋・六本木で公式構内地図の座標を表示圧縮の補助overlayとしてのみ結合しています。

歩行空間ネットワーク用には `src/domain/walkingNetwork.ts` を追加した。公開CSVのノード（座標・階）とリンク（距離・方向・`route_type`）を、GTFSと同じ `IndoorGraph` 形へ正規化できる。ただしこれはデータソースの区別を保持した別グラフであり、GTFSのstopと座標近接などで接続しない。公式なID対応表が確認できたときだけ、明示的な対応レコードを別途登録する。方向が `99`（不明）のリンクは、方向を推測せず探索対象から除外する。

`src/data/fixtures/akabanebashi-walking-network.ts` は、公開された赤羽橋駅CSV（ノード124件、リンク137件）から、階段・ES・EVを含む連結部分をそのまま抽出した23ノード・22リンクの検証fixtureである。これは変換・方向制御のPoC用であり、完全な駅内経路データでも利用者向け案内でもない。

2026-09-17に、チャレンジ2026公式ページは大江戸線12駅（赤羽橋駅を含む）の歩行空間ネットワーク・構内地図・GTFS-Pathways公開を案内している。一方、以前のODPTカタログに残る「公開終了」表記は2025向けの旧記録であり、2026リソースの可用性や利用条件を判断する根拠にしない。このリポジトリの歩行ネットワーク／構内地図fixtureは検証用抽出として明示し、応募版ではほこナビの2026公開リソースを再取得して、スキーマ・更新日・ライセンスを照合する。

構内地図データは、ODPTカタログに記載された国土地理院「階層別屋内地理空間情報データ仕様書（2019年3月）」準拠として扱う。この版で `F011` は階段、`F012` はエレベーター、`F013` はエスカレーターである。`src/domain/stationMap.ts` は、この根拠を固定した設備POIの表示用正規化に加え、公開GeoJSONとGTFS経路を実際に重ね合わせる `StationMapCompressionOverlay` を定義する。`src/data/stationMaps/akabanebashi/` のB1/B2 GeoJSONをEPSG:6668の経度・緯度として読み込み、GTFS pathwayの端点・中点をSpaceポリゴンへ照合し、同じ設備種別のFacility点を階層と距離（既定15m以内）で対応付ける。このoverlayは経路探索には使わず、同一Space・同一Facilityと確認できた短い通路リンクだけを表示圧縮する補助に限る。GTFSの半階（例: -0.5）は隣接する公開階（-1）との照合にだけ使い、利用者向けの階名は推測しない。

`compactIndoorRouteSteps` は、連続する通路をまとめる。施設種別は勝手に統合せず、階段・ES・EVの途中にある短い通路を吸収できるのは、公開構内地図の overlay が「同一Facilityかつ同一Space」と示した場合だけである。例外として、同一階・2m以下・分岐なしで、公開map overlayが両方のエッジを裏付けるエレベーター接続リンクは、隣接する上下移動へ表示上だけ吸収する（Facility IDはprovenanceに保持する）。改札・退出改札は統合しない。案内板名、左右、施設名などは加えない。`src/domain/indoorRouting.test.ts` では、未登録の乗降位置を拒否すること、fare gateを候補比較で失わないこと、provenance、同一設備内の安全な圧縮と別設備を統合しないこと、同一階エレベーター接続の分岐安全策、12駅validationを検証する。
六本木駅については、ほこナビDPの[構内地図GeoJSON resource](https://ckan.hokonavi.go.jp/dataset/mlit_station_oedo_roppongi)（取得日 `2026-09-21`）を `src/data/stationMaps/roppongi/` に保存し、Facility 24ファイル、Space 8ファイル、Floor 8ファイルを読み込む。付属する歩行空間ネットワークの `node.geojson` / `link.geojson` も同ディレクトリの `walking-network/` に保存するが、今回もGTFS-Pathwaysを経路探索の正本とし、歩行空間ネットワークは補助検証データとして扱う。六本木2番ホーム→7出口では、`424L0239`・`424L0151`・`424L0104` が同一のF012エレベーターFacilityに照合され、1つの「エレベーターで上がる」へ圧縮される。
国立競技場駅も同じ方法で、ほこナビDPの[構内地図resource](https://ckan.hokonavi.go.jp/dataset/station_oedo_kokuritsu-kyogijo)（取得日 `2026-09-21`）からFacility 5ファイル、Space 5ファイル、Floor 5ファイルと、歩行空間ネットワークの `node.geojson` / `link.geojson` を `src/data/stationMaps/kokuritsu-kyogijo/` に保存した。A2経路の `426L0165` と `426L0220` / `426L0290` は、前者と後者でF012 Facility IDが異なるため設備としては統合しない。一方、`426L0165` は同一階・1.6m・分岐のない接続エッジで、公開map overlayが両エッジを裏付けるため、表示上は直後の上下移動へ吸収する。結果として施設IDはprovenanceに残したまま、「エレベーターで上がる」1ステップとして案内する。

## ODPT で置き換える候補と、手確認が必要な範囲

ODPTの公開カタログ確認（2026-09-20）では、小田急電鉄は「駅情報」「路線系統情報」「駅時刻表」「乗降者数情報」の4データセットを掲載しています。駅施設、列車ロケーション、構内徒歩経路グラフはこの一覧では確認できませんでした。確認内容の詳細は [ODPTデータ確認メモ](docs/odpt-data-audit.md) を参照してください。

許諾を満たすサーバー側アダプターから以下を置換します。ブラウザにはODPT APIキーを置かず、必要なら自前のバックエンド/同期ジョブで取得・正規化します。

| 範囲 | ODPT等で自動化を検討 | 人が公式根拠で確認・登録 |
| --- | --- | --- |
| 駅・路線 | 駅、路線、事業者の識別子・名称 | 表記の読みや利用者向け名称 |
| 列車 | 平日時刻表、列車種別、方向、番線（提供される場合） | 紙への採用可否、当日の変更対応 |
| 駅構内 | 駅施設・出入口データが提供される場合の照合 | 到着ホームから改札/出口までの連続した歩行動線、バリアフリー代替 |
| 徒歩 | 駅出口座標など提供範囲の照合 | 目的地までの安全な徒歩経路、横断箇所、所要時間、地図形状 |

ODPTが駅構内の詳細な徒歩経路グラフを提供するとは仮定しません。構内動線は `StationGuide` の検証済みレコードで管理し、未知の駅では安全な代替案内だけを出します。

## ODPT 利用時の確認事項

- ODPTは利用者登録後に発行されるAPIキーでアクセスします。キーはサーバー環境変数にだけ保管します。
- 実装前にデータカタログで小田急電鉄の対象リソース、スキーマ、更新頻度、個別利用条件を確認します。未確認のAPIエンドポイントやフィールド名は実装していません。
- 動的データを表示する場合はAPIの生成時刻（`dc:date`）を表示し、有効範囲・更新頻度に従います。静的データは取得日時を表示し、更新を追跡します。
- 公開時は、公共交通オープンデータセンターを出典として表示し、正確性・完全性の非保証とアプリの問い合わせ先を明記します。データごとの個別利用条件も確認します。

参考: [ODPT 開発者サイト](https://developer.odpt.org/)、[開発者ガイドライン](https://developer.odpt.org/terms/data_basic_use_guideline.html)、[基本ライセンス](https://developer.odpt.org/terms/data_basic_license.html)。
